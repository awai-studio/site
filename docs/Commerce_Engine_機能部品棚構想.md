# Commerce Engine 機能部品棚構想

作成日：2026年8月9日  
位置づけ：近い将来に着手する共通開発基盤の構想メモ

## 1. この文書の目的

この文書は、上田プロジェクトとAwai Studioの完成後に始める「Commerce Engine」について、目的、着手順序、設計原則を忘れないために残すものである。

Commerce Engineは、上田やAwaiを一つの巨大なアプリへ統合する計画ではない。実案件で動作確認できた機能を、別案件へ安全に持ち運べる「機能の部品棚」として蓄積する計画である。

## 2. 現在の優先順位

着手順序は次のとおりとする。

1. 上田プロジェクトで実証済みのセキュリティ、フォーム、計測、メニュー、モーダル等を棚卸しする
2. Awai Studioに必要な共通機能を、Awaiの構成へ適合させて移植する
3. Awai Studioの記事CMS、カレンダー、予約、管理、メール、計測を完成させる
4. 上田とAwaiをそれぞれ独立したアプリとして完成・検証する
5. その後、実証済み機能を抽出してCommerce Engineプロジェクトへ登録する

Commerce Engineを先に作り込んではならない。実案件で動いていない想像上の共通機能を増やすと、使いにくい巨大基盤になるためである。

## 3. 三つのプロジェクトの役割

### 上田プロジェクト

フォーム入力を中心とした実証案件とする。

主な資産：

- 入力フォーム
- ブラウザ側・API側の入力検証
- Supabase保存とRLS
- ファイル検証と非公開Storage
- 自動返信と管理者通知
- 管理権限
- Bot、二重送信、過剰送信対策
- GA4、GTM、UTM計測
- グローバルメニュー、スマホメニュー、モーダル

### Awai Studio

記事管理と文化体験の予約を中心とした実証案件とする。

主な資産：

- 許可された執筆者のログイン
- Word風編集とMarkdown原文編集
- 下書き、プレビュー、公開・非公開
- 画像アップロード
- 英語本文の後に日本語本文を続ける記事形式
- 記事一覧、記事詳細、SEO、OGP、RSS
- カレンダー、空き枠、定員
- 予約、状態管理、自動メール
- 管理画面
- Stripe決済
- SNS、広告、GA4、GTMの効果計測

### Commerce Engine

公開サイトや顧客向けサービスではなく、複数案件へ機能を配布する共通開発基盤とする。

上田とAwaiはCommerce Engineの中へ統合しない。それぞれ独立した本番案件として残す。

## 4. 巨大な全部入りアプリにしない

Commerce Engineは、次の三層に分ける。

### 最小スターター

新規案件の出発点だけを持つ。

- Next.jsの基本設定
- 共通レイアウト
- 最低限のスタイル
- 環境変数のひな型
- エラー処理の基本
- セキュリティヘッダーの基本

### 共通パッケージ

複数案件から読み込んで使う、小さく安定した処理を置く。

- 入力検証
- 権限判定
- 日付・金額処理
- 計測イベント
- メール共通処理
- セキュリティ共通処理

### 機能キット

画面、API、データベース、権限、設定、テストを一組として案件へ追加する。

- フォームキット
- 記事CMSキット
- カレンダーキット
- 予約キット
- 決済キット
- 印刷仕様・価格計算キット
- 注文管理キット

新しい案件へは、最小スターターと必要な機能だけを追加する。全部入りアプリを複製し、毎回不要なファイルを大量に削除する方法は採用しない。

## 5. 案件ごとの機能選択例

| 案件 | 利用する主な機能 |
|---|---|
| 上田 | フォーム、メール、管理、計測、セキュリティ |
| Awai Studio | 記事CMS、カレンダー、予約、決済、計測 |
| 自治会情報ポータル | 記事CMS、部会別権限、行事カレンダー、年度別保存 |
| 自費出版注文 | フォーム、仕様選択、部数別価格計算、入稿、注文、決済 |
| 通常通販 | 商品、注文、決済、配送 |

## 6. 共通化の進め方

各機能は、次の手順で共通部品へ昇格させる。

1. 実案件の要求に合わせて実装する
2. 本番相当の環境で正常系・異常系・権限・スマートフォンを確認する
3. 案件固有の文章、画像、名称、料金、URL、メール文面を分離する
4. 変更可能な部分を設定として外から渡せるようにする
5. Commerce Engineへ共通パッケージまたは機能キットとして登録する
6. 空の検証用サイトへ、その機能だけを追加する
7. 別サイトでも動作することを確認してから、再利用可能と判定する
8. 以後の一般的な改善はCommerce Engineへ反映し、必要な案件へ戻す

Awaiの中で動いただけでは、まだAwai専用機能かもしれない。空の検証用サイトへ移して動いた時点で、本当の共通部品とする。

## 7. すべてを共通化しない

次のものは案件固有として残す。

- ブランドとデザイン
- 写真、文章、翻訳
- 商品名、体験名、料金
- 営業時間、定員、キャンセル条件
- 契約、保険、法的表示
- 顧客固有の業務手順

共通化するのは、保存、検証、権限、通知、計測などの難しく繰り返し発生する部分である。案件固有部分まで無理に設定化しない。

## 8. 修正の戻し方

不具合や改善が見つかった場合、次のように扱う。

- 案件固有の修正は、その案件だけで直す
- 他案件にも当てはまる修正は、Commerce Engineの共通部品へ反映する
- 共通部品を更新した後、影響を受ける上田・Awai・将来案件で再テストする
- 上田にはフォームやセキュリティに関係する改善だけを戻す
- Awaiには記事CMS、予約、計測等に関係する改善だけを戻す

共通部品を直したからといって、関係のない機能を全案件へ入れない。

## 9. 共通部品の完成条件

次を満たした機能だけを部品棚へ登録する。

- 元の実案件で動作確認済み
- 案件固有情報が分離されている
- 必要な設定と依存関係が明記されている
- データベース変更手順が用意されている
- 権限とセキュリティ条件が明記されている
- PCとスマートフォンで確認済み
- 空の検証用サイトへ単独で追加できる
- 導入手順、テスト項目、更新履歴が残されている

## 10. Commerce Engine着手時の最初の作業

上田とAwaiが完成した後、次の順で開始する。

1. 上田とAwaiの機能一覧を作る
2. 「共通化する」「案件固有」「まだ判断しない」に分類する
3. Commerce Engineの最小スターターを作る
4. 上田のフォーム基盤を最初の機能キットとして取り出す
5. Awaiの記事CMSを二番目の機能キットとして取り出す
6. Awaiのカレンダー・予約を三番目の機能キットとして取り出す
7. 空の検証用サイトで各キットを個別に試す

印刷仕様・部数別価格計算・自費出版注文は、上記の基盤が安定した後に、独立した機能キットとして設計する。

## 11. 将来この作業を再開するCodexへの指示

Commerce Engineに着手する前に、この文書と`Awai_Studio_今月実行計画.md`を読むこと。

次の原則を守ること。

- 上田とAwaiを一つのアプリへ統合しない
- Commerce Engineを全部入りの本番アプリにしない
- 実案件で確認していない機能を先回りして大量に作らない
- 元案件を壊さず、複製または抽出先で共通化する
- 機能単位で導入・除去できる境界を優先する
- 共通化によって元案件が複雑になる場合は、無理に共通化しない
- 共通部品に昇格させる前に、別の空サイトで動作確認する

この構想の目的は、コードの量を増やすことではない。案件を重ねるたびに、安全性、品質、開発速度、運用ノウハウを会社の資産として蓄積することである。
