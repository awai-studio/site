# 上田からAwaiへの共通機能移植棚卸し

作成日：2026年8月9日

## 目的

上田プロジェクトで実証した機能を、Awai Studioへ安全に移植する。完成コードを丸ごと貼り付けるのではなく、Awaiの事業、画面、データ構造へ適合させる。

## 分類

| 機能 | 判定 | Awaiでの扱い |
|---|---|---|
| API側の入力検証 | 調整して移植 | 体験、人数、日付、時間、氏名、メール、本文をサーバー側で再検証する |
| ハニーポット・最短入力時間 | 調整して移植 | JSON予約フォーム用の項目名と処理へ変更する |
| リクエスト形式・容量検証 | 調整して移植 | JSON、32KB上限として適用する |
| 二重送信防止 | 次段階 | Supabaseの予約テーブルへ受付トークンと一意制約を追加して実装する |
| 接続元ごとの回数制限 | 次段階 | 上田のRPCをそのまま使わず、Awai用DB変更を作成してから適用する |
| PDF検証・非公開Storage | 今は移さない | 現在の予約フォームにはPDF添付がない |
| メール失敗とDB保存の分離 | 調整して移植 | 保存後のメール失敗で予約を再送させない |
| 管理者ログイン・権限 | 調整して移植 | 記事CMSと予約管理で共通利用する役割へ再設計する |
| グローバル・スマホメニュー | 調整して移植 | Awaiの英語導線、デザイン、タッチ操作へ置き換える |
| 共通モーダル | 改善して移植 | Esc、背景クリック、スクロール固定に加えフォーカス移動を改善する |
| GA4・GTM・UTM | 調整して移植 | Awai用イベント名、環境変数、予約・記事導線へ変更する |

## 第一段階で実施する内容

- 予約APIのContent-Typeと容量を検証
- クライアントから送られた体験名を信用せず、サーバー側の体験データを正本にする
- 体験ID、人数、希望日、希望時間を許可値で検証
- 予約可能期間、曜日、除外日をAPI側でも検証
- 氏名、メール、メッセージの形式と最大長を検証
- ハニーポットと最短入力時間を追加
- DB保存後のメール失敗を予約受付失敗として扱わない
- 内部ログへ予約本文や個人情報を出さない

## 次段階

1. 予約テーブルの現行定義を確認する
2. 受付トークンと一意制約による二重送信防止を追加する
3. Awai用の回数制限テーブルとRPCを追加する
4. グローバルメニュー、スマホメニュー、共通モーダルを移植する
5. GTMとUTM保存を移植する

## 移植原則

- 元の上田は変更しない
- Awai固有の要件を優先する
- DB変更が未適用の機能を見切りで有効化しない
- 外部サービスが失敗しても、保存済み受付を失わない
- 一段階ごとにビルドと異常系を確認する
- Awaiで実証後、将来Commerce Engineの機能キット候補にする
